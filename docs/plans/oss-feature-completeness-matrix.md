## Status vocabulary and notation

- **Source-present:** concrete caller/handler/execution code exists. This does not establish a successful deployed workflow.
- **Integration gap:** inspected layers disagree or do not complete the advertised end-to-end behavior; reproduce before representing it as a confirmed live defect.
- **Unqualified:** code exists, but the inspected source does not establish the required runtime/data/portability behavior.
- **Helper/catalog only:** a utility or catalog record exists without a complete observed consumer path; do not count it as a delivered user feature.

Paths below are relative to the OSS repository. UI aliases reduce repetition: **Server page** = `web/carbon-panel/src/routes/servers/[id]/+page.svelte`; **Components** = `web/carbon-panel/src/lib/components/`; **Services** = `internal/rpc/services/`; `routes/` and `lib/` paths are under `web/carbon-panel/src/`. Every future acceptance scenario must include actual source version, selected node identity, initial data, actor permissions, action, result and recovery evidence.

## Completeness is an end-to-end claim

A feature becomes qualified only after a user can invoke it, the intended authorized runtime/storage receives the operation, the outcome is observed, failures are visible/recoverable, and persistent data survives interruption. A tab, protobuf, helper, README statement or passing shallow mock proves a narrower fact.

The broad source inventory is substantial: server power/configuration, remote Docker pools, players/commands, file tooling, mods, pack catalogs/Studio, backups/S3, tasks/chains, sleep/wake, proxy routing, modules, permissions and support all have concrete source. This Epic should preserve them while resolving integration and recoverability gaps.

For each row, the implementing issue should name the selected deployment profile and full error behavior. If remote semantics are not implemented safely, reject the operation explicitly with a capability explanation; never silently execute against a local daemon or controller directory. Shared-filesystem deployments must be declared and verified, not inferred from matching path strings.

## Cross-cutting acceptance journeys

J01: Fresh supported deployment → select node/runtime → create → externally join → edit safe settings/content → restart without losing world.
J02: The same workflow on a remote daemon whose filesystem is not shared with the controller.
J03: Backup/export → destroy only disposable runtime → restore to a clean allocation → verify the named world and game connection.
J04: Concurrent stop/recreate/backup/update/sleep and controller/daemon failure → one authoritative operation outcome, no duplicate writer, no silent rollback of user intent.
J05: Delegated user operates one allowed server, then loses access during a stream/transfer/task; all execution paths enforce revocation policy.
J06: Node unavailable, full disk, registry outage or bad modpack → meaningful diagnosis and safe retry/rollback; no false ready or destructive “repair.”
J07: Upgrade/rollback/reinstall with persistent DB/worlds/backups and an intentional stopped server → owned data and desired state preserved.

Source findings here require reproduction at the real caller seam before bug severity or remediation completeness is asserted. The [Docker research](../research/docker-failure-semantics-and-recovery.md) supplies current primary-source behavior and fault-injection proposals.
